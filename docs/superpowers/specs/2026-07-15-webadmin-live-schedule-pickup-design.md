# Live-подхват изменений расписания из веб-админки — дизайн

**Дата:** 2026-07-15
**Статус:** утверждён пользователем в диалоге, ожидает записи в implementation-плане

## Контекст и проблема

Веб-админка (`webadmin/`) редактирует `TaskConfig` напрямую в той же Postgres, что
использует бот, и сама пересчитывает `next_run_at` при сохранении (`compute_next_run`
с `after_change=True`). Но у уже запущенного бота в памяти живёт свой APScheduler —
запись в БД саму по себе не переустанавливает и не создаёт живой job в этом процессе.
Сейчас единственные способы, которыми уже запущенный бот узнаёт о новом/изменённом
расписании — это (1) рестарт бота (`recover_jobs` читает `next_run_at` из БД заново)
и (2) синк с Google Sheets, который для реально изменившихся в таблице конфигов
вызывает `SchedulerService.rebuild_config_job`. Задачи, созданные или переставленные
ТОЛЬКО через веб-админку, никогда не проходят через путь (2) — они просто никогда
не получат живой job, пока бот не перезапустят вручную. Пользователь хочет уйти от
Google Sheets полностью, поэтому полагаться на путь (2) как на побочный механизм
подхвата веб-админских правок нельзя.

## Решение

Новое поле `TaskConfig.pending_rebuild: bool` (default `False`, обычная
Alembic-миграция, `server_default='false'`) — флаг «этому конфигу нужен пересчёт
живого job'а в боте».

**Веб-админка** (`webadmin/routers/tasks.py`, `task_create`/`task_update`) вместо
того, чтобы самой звать `compute_next_run`/писать `next_run_at`, теперь просто
выставляет `cfg.pending_rebuild = True` и коммитит. Единственный источник истины
по пересчёту расписания остаётся в уже существующем
`SchedulerService.rebuild_config_job` — веб-админка больше не дублирует эту логику.

**Новый интервальный job в боте** — `pending_rebuild_job(bot, session_factory,
scheduler_svc)`, по образцу уже существующих `auto_sync_job`/`delivery_log_job`:
1. Находит все `TaskConfig` с `pending_rebuild=True` (новый метод
   `TaskRepository.get_pending_rebuild() -> list[TaskConfig]`).
2. Для каждого вызывает `scheduler_svc.rebuild_config_job(config_id)` — уже
   пересчитывает `next_run_at` (`after_change=True`) и переустанавливает/снимает
   APScheduler-джоб.
3. Сбрасывает `pending_rebuild = False`, коммитит.

**Регистрация:** `SchedulerService.register_pending_rebuild_job()` — по образцу
`register_sync_job()`, но БЕЗ переключателя `enabled` в настройках (это не
опциональная фича вроде синка с Sheets, а базовая корректность работы
веб-админки — всегда включён). Интервал фиксирован на **30 секунд**, не
настройка (пользователь явно выбрал фиксированное значение, не хочет
конфигурировать через `/admin`). Регистрируется при каждом старте бота
(`bot/main.py`, рядом с остальными `register_*_job()`), один раз, без
remove/re-add по требованию настроек (раз нет `enabled`-переключателя — нет и
необходимости пересобирать job при изменении настройки).

### Явно вне рамок

- Никакого нового HTTP-эндпоинта у бота, никакого прямого межпроцессного
  вызова — переиспользуется ровно тот же паттерн «поллинг-джоб читает флаг в
  БД», что уже работает для Sheets-синка и логов.
- Users/Topics/Articles CRUD в веб-админке не затрагиваются — у них нет
  живого APScheduler-состояния, которое надо было бы подхватывать.
- Отключение самого Google Sheets (`sync.auto_enabled` и т.д.) — отдельное
  решение пользователя, делается ПОСЛЕ того, как этот механизм заработает и
  будет проверен.

## Тестирование

- `TaskRepository.get_pending_rebuild()`: возвращает только конфиги с
  `pending_rebuild=True`, не возвращает конфиги с `pending_rebuild=False`.
- `pending_rebuild_job`: для конфига с `pending_rebuild=True` вызывает
  `rebuild_config_job` (замокать `scheduler_svc`, проверить вызов с правильным
  `config_id`) и сбрасывает флаг в `False`; для конфига с `pending_rebuild=False`
  ничего не делает.
- `webadmin` (`test_tasks_crud.py`): создание/редактирование активной задачи
  через веб-форму выставляет `pending_rebuild=True` (не считает `next_run_at`
  само — заменить существующий тест `test_create_task_sets_next_run_at_for_today_when_active`
  на проверку `pending_rebuild=True` вместо `next_run_at is not None`).
- Интеграционный сценарий (можно как unit-тест с реальным `AsyncIOScheduler`,
  без реального ожидания 30 секунд — вызвать `pending_rebuild_job` напрямую):
  конфиг создан с `pending_rebuild=True` → после вызова job'а зарегистрирован
  `config:{id}` APScheduler-джоб И `pending_rebuild` сброшен в `False`.

## Критерии готовности

1. Задача, созданная или изменённая (расписание/активность) через веб-админку,
   в течение 30 секунд начинает жить в APScheduler уже запущенного бота — без
   его перезапуска и без зависимости от Google Sheets.
2. Веб-админка сама больше не считает `next_run_at` напрямую — только
   выставляет флаг; фактический пересчёт делает существующий
   `rebuild_config_job`.
3. Job включён всегда, без отдельной настройки `enabled`/`interval_minutes`.
